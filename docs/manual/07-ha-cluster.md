# 7. 高可用叢集

**情境：** 認證不能停。三台 rradius 組成叢集，資料自動複寫到每一台；任一台停機（故障、升級、重開機）時，另外兩台照常服務，NAS 自動改問活著的節點。

範例目錄：[`rradius-server/examples/scenarios/ha-cluster/`](../../rradius-server/examples/scenarios/ha-cluster/)

| 檔案 | 內容 |
| --- | --- |
| `node1.toml`、`node2.toml`、`node3.toml` | 三個節點的設定，只差 `node_id`、`listen` 和 `[metrics] bind` |
| `raft.secret`、`api.secret` | 叢集內部的密碼，三台相同 |
| `nas.secret` | NAS 的共用密碼，三台相同 |
| `accounting.lua` | 計費腳本，和[第 2 章](02-quick-start.md#accountinglua-做了什麼)說明的相同 |
| `migrations/1_schema.sql` | 資料表，和快速開始相同 |
| `migrations/2_demo_users.sql` | 示範帳號 alice、bob、carol，**正式環境要刪掉** |

帳號和計費和快速開始相同，所以這一章只講叢集本身。

## 架構

```
             NAS（主：node1，備：node2、node3）
              │ RADIUS 1812/1813
   ┌──────────┼───────────────┐
 node1      node2           node3       每台都有完整的資料
 10.99.0.1  10.99.0.2       10.99.0.3   （WireGuard 位址）
   └──── raft 8100 / api 8200 ────┘     節點之間只走 WireGuard
```

- **寫入（`sql_execute`、migration）經過 Raft，** 要多數節點（3 台中的 2 台）同意才成功，所以每台寫入的結果都相同。
- **讀取（`sql_query`、`sql` 處理器）讀本機副本，** 很快，但可能比剛寫入的資料慢一點。
- **三台是最小的高可用：** 停一台還有多數；兩台時停一台就沒有多數。五台可以同時停兩台。

| 狀況 | 認證 | 計費 |
| --- | --- | --- |
| 三台都在 | 正常 | 正常 |
| 停一台 | 正常（NAS 改問其他台）。停的剛好是 leader 時，約 7 到 8 秒內（選舉約 6 到 7 秒，其餘約 1 秒是用戶端重連，見〈跨機房〉），要寫入的登入不回應、計費寫入逾時 | 正常；停的是 leader 時，那段時間的計費進暫存（可能重複一次，見下方） |
| 停兩台，剩一台 | 只讀資料的認證（`sql`、`ldap`）讀本機副本，照常回應；要寫入的（驗證碼、IP 配發）**不回應**，讓 NAS 重送或改問別台。設了 `stop_without_leader_ms` 時，超過那段時間連只讀的認證和 Status-Server 都不回應 | 寫不進去，有計費暫存時先寫在本機並回覆，叢集恢復後重放 |

- **資料庫不能用時不回應，而不是拒絕。** 登入因為叢集資料庫逾時或找不到 leader 而無法決定時，RADIUS 不回覆、TACACS+ 回 ERROR，這樣 NAS 和設備會改問其他節點，使用者也不會看到「密碼錯」。計入 `rradius_radius_discarded_total{reason="database"}`。確定是帳號不存在、密碼錯，而且腳本的資料庫呼叫都成功，才回拒絕；腳本有一次資料庫呼叫失敗後才拒絕的，也算不能決定。腳本在資料庫失敗後回 `ignore` 時，照常交給下一個處理器。進行中的 EAP 對話會留著，NAS 重送時接著做。
- **`stop_without_leader_ms`（`[cluster]`，預設不設）：** 節點超過這段時間沒有 leader，就連只讀的登入和 Status-Server 都不回應（TACACS+ 回 ERROR），計入 `reason="no_leader"`，讓 NAS 和負載平衡器把它當成故障、改問被隔開的另一側。代價是叢集只剩這一台時，它也不服務。計費照常。改了要重啟。
- **斷線很久的節點回來後可能要重啟一次。** 它不在的期間寫入超過 10 萬筆（`snapshot_every`）時，回來後 hiqlite 讀不到自己的日誌，rradius 會記錄 `exiting so that a restart recovers it` 並以狀態碼 1 結束；重新啟動後它會追上叢集。所以每個節點都要設自動重啟（systemd `Restart=on-failure`、Docker `restart: unless-stopped`）。
- **剩一台時不要重啟它。** 正在跑的那台會繼續服務只讀的登入，但重新啟動後要等到有 leader 才起得來（這是 hiqlite 的行為），有 `migrations_dir` 時等 `migrations_wait_ms` 後以狀態碼 1 結束。先救回其他節點。
- **被隔開的節點讀的是舊資料。** 它和多數節點斷開時，在另一側停用的帳號、刪掉的 NAS、撤掉的金鑰，在它這裡都還有效，SIGHUP 也沒用，直到網路恢復。不能接受的話設 `stop_without_leader_ms`。
- **交給叢集的寫入會等結果。** 資料庫很慢（例如 leader 在做快照）或換 leader 時，腳本已經交給叢集的寫入不會中途放棄，會等到叢集回覆（最多 30 秒），所以這筆寫入不會「回報失敗、其實寫進去了」。但計費仍可能記兩次：30 秒內都沒有結果時，計費不回覆、由 NAS 重送；等得比時限久時，同一個請求之後的資料庫呼叫會立刻逾時，這筆進暫存、重放時再跑一次；帶 `RETURNING` 的語句照舊以時限為準。所以計費腳本仍要能重複執行（例如用 `INSERT OR IGNORE`、以 `Acct-Session-Id` 為主鍵）。

## 步驟

### 1. 每台主機的準備

1. 建 WireGuard 網路 `10.99.0.0/24`，三台互為 peer，並用防火牆讓 8100、8200 只收 `wg0` 的連線。完整步驟在 [usage 2.2 節](../usage.md#22-cluster)。
2. 把 `examples/scenarios/ha-cluster/` 整個目錄複製到每台（例如 `/etc/rradius/ha-cluster/`）。
3. **換成自己的帳號：** 第一次啟動前刪掉 `migrations/2_demo_users.sql`，裡面的示範帳號用公開的密碼。之後設定 `[accounts]` 用 `rradius-server user add` 新增，在任何一台節點上執行都會寫到整個叢集；或在 `migrations/` 新增 `2_users.sql`，格式見[第 2 章](02-quick-start.md)和[第 11 章](11-operations.md#帳號和資料)。
4. **每台的 `raft.secret`、`api.secret`、`nas.secret` 和 `migrations/` 要相同。** 先產生新的密碼再複製過去：

   ```bash
   (umask 077; openssl rand -base64 32 > raft.secret; openssl rand -base64 32 > api.secret)
   ```

### 2. 啟動

三台各自啟動自己的設定，順序不拘：

```bash
rradius-server server --config /etc/rradius/ha-cluster/node1.toml   # 在 node1
rradius-server server --config /etc/rradius/ha-cluster/node2.toml   # 在 node2
rradius-server server --config /etc/rradius/ha-cluster/node3.toml   # 在 node3
```

- 第一次啟動時，每台都等叢集組成（多數節點上線），再套用 migration，最多等 `migrations_wait_ms`（範例 120 秒）。一台先起來、其他的還沒起來時，它會等待，不是故障。
- 看到 `RADIUS Server listening` 就能服務。
- **NAS 的設定：** 三台都設成 RADIUS 伺服器，主備或輪流都可以，共用密碼相同。EAP 的一次登入要在同一台完成（第 3 章），所以用 EAP 時選主備，或讓負載平衡器依來源固定節點。

### 3. 確認

RADIUS 走節點的實體位址，不是 WireGuard 位址；請求也要從 client 名單內的主機送出（範例是 `10.80.0.0/16`），否則不會有回應。從那個網段的一台主機，用上面第 3 項加的帳號：

```bash
# 每台都能登入（192.0.2.11 到 .13 換成三台的實體位址）
for ip in 192.0.2.11 192.0.2.12 192.0.2.13; do radtest <帳號> <密碼> $ip 0 "$(cat nas.secret)"; done

# 每台的指標，在節點上或從 WireGuard 網路內
curl -s http://10.99.0.1:9812/metrics | grep rradius_
```

管理用的主機不在 client 網段時，暫時加一個只有它位址的 `[[radius.clients]]`（SIGHUP 套用），測完再移除。

在 node1 送 Start、在 node3 送 Stop，`accounting` 表裡是同一列：寫入經過叢集，哪一台收到都一樣。

一次看三台在做什麼，在任一台執行：

```bash
rradius-server status --config /etc/rradius/rradius.toml --cluster --watch
```

每台一列：角色（leader／follower）、`/readyz`、登入與計費的每秒量、丟棄、處理中，最後一列是合計。各台的 metrics 位址是成員 api 位址的主機配上這台的 `[metrics]` port，所以三台的 `[metrics]` 都要綁 WireGuard 位址（像上面的 `10.99.0.1:9812`）、port 相同；連不到的那台會列為 unreachable 並寫出原因。說明見 [usage 2.8 節〈`status` 指令〉](../usage.md#看這台節點現在在做什麼status-指令)。

## 設定說明

```toml
[cluster]
node_id = 1
listen = "10.99.0.1"
migrations_dir = "migrations"
migrations_wait_ms = 120000

[[cluster.nodes]]
id = 1
raft = "10.99.0.1:8100"
api = "10.99.0.1:8200"
# ...id 2、3 相同
```

- **每台都列出全部三個節點（包含自己），** `node_id` 指出自己是哪一個，一定要有編號 1。
- **`listen` 寫明 WireGuard 位址。** 有 `[[cluster.nodes]]` 時預設是 `0.0.0.0`，會在所有介面上開 raft 和 api，而這兩個埠的連線沒有加密；沒有明確寫 `listen` 時，啟動、重新載入和 `check` 都會記一行警告（`cluster.listen is not set`）。Docker 與 Kubernetes 的範例在容器裡必須接受其他節點，所以明確寫了 `listen = "0.0.0.0"`；放在實體主機上時改成它的 WireGuard 位址。
- **`[lua] query_timeout_ms = 2000`：** 失去多數節點時，寫入要等這麼久才失敗、計費才寫進暫存。預設 5 秒比很多 NAS 的重送間隔長，重送會被當成處理中而丟棄。
- **`[radius.accounting_spool]`：** 各節點只重放自己的暫存檔，所以放在持久的磁碟。`rradius_acct_spool_bytes` 大於 0 代表有還沒寫進資料庫的計費，可以用來告警。
- **`[log] format = "json"`：** 三台的記錄送到同一個收集系統時比較好處理。

### 哪些東西是每個節點自己的

資料表會自動複寫，但下面這些不會。規劃多節點時逐項確認：

| 東西 | 每個節點 | 要注意 |
| --- | --- | --- |
| 設定檔、腳本、字典、`migrations/` | 各自一份 | 內容要相同。改了之後每台都要更新，並各自送 SIGHUP 或重啟 |
| `raft.secret`、`api.secret`、NAS 的共用密碼檔 | 各自一份 | 內容要相同 |
| 憑證、私鑰、撤銷清單 | 各自一份 | 更新時每台都要換並送 SIGHUP |
| 計費暫存 | 只重放自己的檔案 | 放在持久的磁碟；節點壞掉時，它還沒重放的就遺失了 |
| 進行中的 EAP 對話 | 只在收到它的節點 | 同一次登入要留在同一個節點 |
| 叢集狀態 | 各自看 | `/metrics` 的 `rradius_cluster_leader`、`rradius_cluster_is_leader`、`rradius_cluster_applied_index`、`rradius_cluster_seconds_without_leader` |
| 指標、`[log.trace]` 的計時 | 各自的 | 叢集的總和由監控系統加總；追蹤要對有關的每一台都設 |

### 調整

- **`read_connections`：** 讀本機資料庫的連線數，預設是 CPU 數的兩倍（最多 32）。登入大多是讀取，連線不夠時要排隊。記憶體很緊時可以調低，每條連線有自己的快取。
- **`snapshot_every`：** 每累積這麼多筆寫入，節點就做一次快照，預設 100000。調低的話，異常結束（斷電、SIGKILL）後重新啟動比較快，但寫入多時快照太頻繁會拖慢服務。
- **多節點不會提高寫入的上限。** 每筆寫入都要經過同一個 leader、等多數節點確認。登入（讀取）則是每個節點各自處理，節點越多越快。分開的主機之間，每筆寫入還要多等節點之間的往返。

這三項的量測和說明見 [usage 2.2 節](../usage.md#22-cluster)。改了都要重新啟動。

## 日常操作

### 升級或重開機

一次一台：停掉一台 → 升級 → 啟動 → 確認它回到叢集 → 再做下一台。每次只停一台，叢集一直保有多數。

- **確認回到叢集：** 記錄有 `cluster node N has caught up with the cluster`，`/metrics` 的 `rradius_cluster_leader` 是 1。節點啟動時會等有 leader、再等本機副本追上叢集已經寫入的資料，才開始回應，所以停機期間新增的帳號在它第一次回應時就看得到。等待的上限是 `migrations_wait_ms`；沒設 `migrations_dir` 又等不到時，它記一行警告後照常服務（可能用到舊資料）。
- **最後才停 leader。** `rradius_cluster_is_leader` 是 1 的那台最後做：停掉 leader 時要重新選舉，約 7 到 8 秒內的寫入會逾時（原因見〈跨機房〉）。

- **用 SIGTERM 或 Ctrl+C 停止，** 節點先讓 `/readyz` 回 503、照常回應 5 秒讓負載平衡器移出它，再停止接收、等處理中的請求回應完，最後乾淨關閉資料庫（hiqlite 再等 9.5 秒），多節點時要 15 秒左右，所以 `docker stop` 要用 `-t 30` 或設 `stop_grace_period: 30s`。兩段等待可以用 `[shutdown]` 調整（[usage 2.16 節](../usage.md#216-停止-shutdown)）。SIGKILL（`kill -9`、容器被強制停止）不會，下次啟動時本機資料庫會從其他節點重建，比較慢。

### 加新的 migration

1. 把新檔案（例如 `3_add_column.sql`）放到**每一台**。
2. 逐台重啟。第一台重啟時套用到整個叢集，其他台重啟時看到已經套用。
3. 不要讓目錄內容不同的節點同時啟動，見 [usage 2.5 節](../usage.md#25-資料表-migration)。

### 換掉壞掉的節點

主機壞掉、資料救不回來時，換一台新主機頂替它：

1. 新主機用**同一個 `node_id`**、同樣的位址（`[[cluster.nodes]]` 裡它的 `raft`、`api`），設定檔、`raft.secret`、`api.secret`、`migrations/` 和其他台相同。增減過節點時，`[[cluster.nodes]]` 要列出目前所有成員，見〈增加節點〉。
2. `data/` 是空的。舊主機的資料還在但不能信任時，整個刪掉再啟動。
3. 啟動。它從其他節點取得整份資料，記錄出現 `cluster node N has caught up with the cluster` 後才開始回應。
4. 確認：`/metrics` 的 `rradius_cluster_applied_index` 和其他台相同，`rradius_cluster_leader` 是 1；用一個它停機期間新增的帳號在它上面登入一次。

- **其他兩台要在線上。** 新節點要從多數節點取得資料；三台壞兩台時，見 [usage 2.2 節](../usage.md#22-cluster)〈沒有多數節點時重新啟動〉。
- **壞掉的是 leader 也一樣。** 剩下兩台會自己選出新 leader：登入在 1 秒左右恢復，約 7 到 8 秒內的寫入會逾時（選舉約 6 到 7 秒，加上用戶端重連，見〈跨機房〉），計費進暫存後補送。
- **leader 已經做過快照、丟掉舊紀錄也沒關係，** 新節點會直接收到快照。
- **管理指令會等久一點。** leader 剛停止的那段時間，`rradius-server user` 這類指令會先連到舊 leader，等連線逾時才改連新的，可能要十幾秒才完成（上限 30 秒）。
- **測過的範圍：** 2026-11-13 用 `compose.cluster.yaml` 的三節點，在一台主機的 Docker 上模擬主機壞掉（強制停止，刪掉容器和資料 volume）。換掉 follower 約 2 秒追上；設 `snapshot_every = 50`、寫入約 200 筆讓 leader 做過快照後換掉 leader，約 5 秒追上，三台的 applied index 相同，期間新增的帳號在每台都能登入。沒有在多台實體主機或經過 WireGuard 的環境測過。

### 增加節點

叢集在執行中就能加一台，其他節點不必停：

1. 新主機用一個沒用過的 `node_id`，設定檔的 `[[cluster.nodes]]` 列出**目前所有成員，包含它自己**（用 `cluster members` 看現在有誰）；`raft.secret`、`api.secret`、`migrations/` 和其他台相同。
2. `data/` 是空的，啟動。它會自己向叢集申請加入，先複製資料，再成為投票成員，記錄出現 `cluster node N has caught up with the cluster` 後才開始回應。
3. 確認：`rradius-server cluster members --config /etc/rradius/rradius.toml` 列出它是 `voter`；用一個既有帳號在它上面登入一次。
4. 把它加進其他每台的 `[[cluster.nodes]]`（還有 WireGuard 的 peer 和防火牆，見 [usage 2.2 節](../usage.md#22-cluster)），之後重啟時生效。不急著改：其他節點不改設定也能照常運作和重啟，但 `user`、`cluster` 這些指令只問設定裡列的節點。

```
$ rradius-server cluster members --config /etc/rradius/rradius.toml
node 1  voter    leader  raft 10.0.0.1:8100  api 10.0.0.1:8200
node 2  voter            raft 10.0.0.2:8100  api 10.0.0.2:8200
node 3  voter            raft 10.0.0.3:8100  api 10.0.0.3:8200
node 4  voter            raft 10.0.0.4:8100  api 10.0.0.4:8200  (not in this configuration)
```

`(not in this configuration)` 表示這份設定還沒列它，提醒你做第 4 步。

- **空資料加入的節點一定要列出現在的 leader。** 它只向自己設定裡列的節點申請加入，其他節點只會叫它去找 leader；leader 不在它的清單裡就加不進去。實測的設定有 `migrations_dir`，它等到 `migrations_wait_ms` 後結束（記錄 `did not join within`），被 Docker 自動重啟後一直重來。所以列出全部現有成員最保險。2026-11-13 實測：leader 換成 node 4 後，設定只列 1 到 3 的空資料 node 1 加不進去；補上 node 4 後 8 秒就加入。
- **帶著資料重新啟動的節點不受影響。** 它從自己的資料知道成員，設定沒列 leader 也能照常回到叢集（同一次實測約 14 秒）。
- **不要用已經在使用的 `node_id`。** 新節點啟動時，會先問設定裡其他節點叢集現在的成員；叢集裡這個編號的節點位址和自己的不同、而且那個位址還有回應，就拒絕啟動，訊息是 `node id 2 is in use: ...`。沒有節點回應（第一次啟動、叢集停著）、叢集記的就是自己的位址（重開機），或舊位址沒有回應（換掉已停機的主機）時照常啟動。沒有這個檢查時（2026-11-18 的實測），新節點會把叢集裡既有成員的 raft 與 api 位址改成自己的，原來的 node 2 還在回應登入，但叢集已經把它當成別的主機。檢查需要有一台其他節點回應，並用同一個 `secret_api`；加節點前仍先用 `cluster members` 確認編號沒用過。（在三個節點的 Docker 上試過：新主機用 2 號被拒絕，叢集成員不變，node 2 照常登入；node 2 重開機、node 2 停機後由新主機用它的編號，都不被這個檢查擋下。）
- **密鑰不同的節點加不進去，** 新節點的記錄寫出原因：`secret_raft` 不同是 `Invalid ChallengeResponse`（WebSocket 握手失敗），`secret_api` 不同是 `Invalid API Secret`；叢集的成員不變（2026-11-18 實測）。
- **新節點的 `migrations/` 比別台多一個檔案時，** 節點照樣加入、其他節點重啟也照常，沒有記錄提到差異；各節點的 `migrations/` 要保持相同，這個組合沒有深入驗證（2026-11-18 只看了加入與其他節點重啟）。

### 移除節點

要淘汰一台時，順序是**先停機、再移除、最後改設定**：

1. 停掉那台（停止服務或關機），並且之後不再用原來的設定和資料啟動它。
2. 在任何一台還在叢集裡的節點上執行 `rradius-server cluster remove --config /etc/rradius/rradius.toml 4`，印出 `removed node 4` 就完成。指令會自己找到 leader。
3. 從其他每台的 `[[cluster.nodes]]` 刪掉它，之後重啟時生效。

指令會擋下這些情況，什麼都不送：

| 情況 | 結果 |
| --- | --- |
| 那台還在回應 | 拒絕，要你先停機（結束碼 2）；沒有旗標可以跳過 |
| 編號不在叢集裡 | `no node 9 in the cluster`（結束碼 1） |
| 移除後只剩 1 或 2 台投票成員 | 拒絕並說明風險，要加 `--force`（結束碼 2） |
| 它是最後一台投票成員 | 一律拒絕（結束碼 2） |

為什麼一定要先停機（2026-11-13 實測）：

- **被移除但還在執行的節點會用舊資料回答。** 它不再收到新的寫入，移除後新增的帳號在它上面登入會被拒絕，停用的帳號還能登入。NAS 還把它列為 RADIUS 伺服器時，就會得到錯的答案。
- **帶著舊資料重新啟動會卡住，** 登入沒有回應。
- **清空資料、設定還列著自己時重新啟動，會自動加回叢集。** 所以淘汰的主機要把 rradius 的服務關掉，不只是刪資料。
- **管理指令可能卡住。** 設定裡排第一的節點如果「已移除但還在執行」，`user` 這類指令會等到 30 秒逾時；先停機就不會發生。

其他注意事項：

- **維持奇數台（3 或 5）。** 3 台可以壞 1 台，5 台可以壞 2 台；4 台和 3 台一樣只能壞 1 台。只剩 2 台時任何一台停掉都不能寫入，所以指令要求 `--force`。
- **要移除的是 leader 也一樣，** 先停掉它：剩下的節點會選出新 leader（約 7 到 8 秒內的寫入會逾時，見〈跨機房〉），再移除。
- **停機的主機排在設定第一位時，** `cluster members`、`cluster remove` 會多等約 5 秒才換下一台（2026-11-18 實測：主機停機約 5.5 秒，封包被丟約 6.5 秒）；把停機的節點從設定刪掉，或移到後面，就不會。
- **一個叢集失去多數時，`members` 看到的 leader 可能是過期的。** 三台只剩原來的 leader 時，它仍回報自己是 leader（結束碼 0），但它沒有多數，寫入不會成功；剩下的是 follower 時，`members` 約 30 秒後以結束碼 3 結束（`the cluster did not answer within 30 s`）。要判斷能不能寫，看 `rradius-server status` 的 `Has a leader`，或直接試一次寫入。
- **移除 leader 約 5 秒完成，登入不受影響。** 測試程式在移除 leader 期間對剩下的三台各每 0.05 秒登入一次，共約 1,480 次都成功，最長空檔 0.1 秒（登入讀本機副本，不需要 leader）。
- **只停一台不必移除。** 升級、重開機、換硬體後用同一個 `node_id` 回來，見〈升級或重開機〉和〈換掉壞掉的節點〉；移除是給不會再回來的節點。
- **測過的範圍：** 2026-11-13 用 `compose.cluster.yaml` 的三節點，在一台主機的 Docker 上，用 `cluster` 指令操作：加第 4 台 1 到 3 秒成為投票成員、約 4 秒開始回應登入；第 4 台還在執行時移除被拒；停機後移除立刻完成；停掉 leader（約 10 秒）後移除它，連同選出新 leader 約 4 秒完成，之後每台都看得到新帳號；被移除的 node 1 以空資料、列出全部成員的設定重新加入約 8 秒。舊節點不改設定也能帶著資料重啟。沒有在多台實體主機或經過 WireGuard 的環境測過。
- **第二輪的測試（2026-11-18）：** 同樣用一台主機的 Docker（`snapshot_every = 50`，`secret`、`migrations/` 相同，三到五個節點），把增減節點的流程逐項走過一遍，約 60 項檢查，結果與設計相符，只有重複使用 `node_id` 這一項當時沒有被擋下（之後加了啟動時的檢查，見〈增加節點〉），其餘補上面幾條文件。涵蓋：`cluster members`（查看成員、成員與設定的差異、停機或封包被丟的節點排第一、選舉中、沒有多數、密鑰錯誤、用法錯誤）、執行中加入（加第 4、第 5 台、兩台同時加、選舉中加、快照後加、漏列成員、停一台時加）、移除（還在回應、停機、leader、找不到的編號、`--force` 的情形、五個成員時 leader 剛換人或被切斷網路）、移除之後（帶舊資料重啟、清空後重新加入、其他節點改設定重啟）、和其他操作一起（換掉壞掉的節點、新 migration 逐台重啟、寫入中加入與移除：394 次寫入沒有失敗，加入約 3 秒、移除立刻完成）。
- **第三輪的補測（2026-11-18）：** 企業版映像的 `cluster members`、`cluster remove`（node4 加入、停機、移除，輸出與核心相同）；leader 是 node4、node1 已移除時，node1 空資料而設定沒有列 node4 加不進去（`did not join within`），補上 node4 後 9.9 秒內加入；四個節點備份後還原（node1 用備份副本先起來、其他三台自己加入），成員回到四個、資料回到備份的時間點。
- **沒有測：** 經 WireGuard 的多台主機、真實 NAS 在選舉期間的行為。

## 跨機房

三個節點分在不同機房、節點之間隔著幾毫秒到幾十毫秒時，叢集會怎樣？下面是在一台主機上模擬出來的數字，**用來判斷「值不值得往這個方向設計」，不是對真實廣域網路的承諾。**

### 量測條件

- **環境：** Apple M4 Max（14 核）的一台主機，OrbStack 上的 Docker，三個節點各一個容器；映像是核心的 `rradius-server` 加上 `iproute2`。節點設定是 `oss/docker/config/auth.lua` 與 `sql` 處理器（登入讀本機副本，每個計費封包一次 `INSERT`）。
- **延遲怎麼加：** 在每個節點對另外兩個節點的 egress 用 `tc netem` 加單向延遲（來回時間 RTT 的一半），RADIUS 用戶端到節點的路徑不加。RTT 用節點之間的 `ping` 校正到目標附近，**下表一律用實測值**：0.2 ms（沒有加，基準）、約 5 ms（5.1–5.2）、約 20 ms（19.2–20.0）、約 50 ms（50.1–50.5）。
- **模擬的限制：** 只有固定的延遲，沒有抖動、沒有封包遺失、兩個方向相同；節點在同一台主機上，CPU 和記憶體不是瓶頸。
- **負載：** `rradius-bench`，固定並行 64，暖機 2 秒、量測 10 秒，每個 RTT 點 3 次。讀取負載是 `pap` 登入（`sql` 處理器，讀本機副本）；寫入負載是 `acct-start`（每個封包一次 `INSERT INTO accounting`，要經過 Raft）。用戶端打的是當時的 leader。
- **原始數字與腳本：** `tools/cluster-latency/`（工作區 repo）的 `results/*.json`。除分區外，其餘每項重複 3 到 5 次。

### 穩態：讀不受影響，寫入大約和 RTT 成反比

| 節點間 RTT（實測） | 登入（讀）吞吐 | 登入 p50／p99 | 計費 Start（寫）吞吐 | 寫入 p50／p99 |
| --- | --- | --- | --- | --- |
| 0.2 ms | 86,100／s（85,800–86,600） | 0.7／1.4 ms | 42,700／s（41,600–43,500） | 1.3／3.3 ms |
| 5.1 ms | 85,800／s | 0.7／1.5 ms | 3,940／s（3,820–4,050） | 14.6／25.6 ms |
| 19.2 ms | 85,200／s | 0.7／1.5 ms | 826／s（798–857） | 78／119 ms（一次 232 ms） |
| 50.5 ms | 85,300／s | 0.7／1.6 ms | 318／s（301–327） | 198／309 ms |

（括號是三次中的最低與最高；p50／p99 取三次的典型值，每次的數字見 `results/steady.json`。）

- **讀取（`sql` 登入）不隨 RTT 改變。** 讀本機副本，不經過網路。
- **寫入吞吐在固定並行下大約和 RTT 成反比，預期被確認。** 吞吐乘以 RTT 在 5、19、50 ms 分別約 20,000、15,900、16,100，一次寫入的延遲約是 RTT 的 2.9、4.1、3.9 倍。也就是並行 64 時，一個節點的寫入上限大約是 `64 ÷ (4 × RTT)`；要更高要加並行（沒有測）。
- **這些寫入吞吐是對 leader 量的。** 對 follower 送寫入（要先轉給 leader）的吞吐沒有量。

### 殺掉 leader

用 `docker kill`（SIGKILL）殺掉 leader，用戶端每 50 ms 對一個存活的節點送一個會寫入的計費 Start；選舉時間是殺掉到存活節點之一的 `rradius_cluster_is_leader` 變成 1，寫入不可用時間是殺掉到第一個之後送出的寫入得到回應。每點 5 次（5 ms 那點有 1 次沒有觀察到選舉，排除，剩 4 次）。

| 節點間 RTT（實測） | 選舉時間 | 寫入不可用時間 |
| --- | --- | --- |
| 0.15 ms | 5.7–6.9 秒 | 6.7–15.2 秒（5 次中 4 次 15 秒左右） |
| 5.2 ms | 5.0–6.4 秒 | 10.1–15.2 秒 |
| 20.0 ms | 6.0–6.9 秒 | 7.2–17.6 秒 |
| 50.1 ms | 6.4–6.8 秒 | 7.4–17.8 秒 |

（這張表是改用 1 秒重連間隔之前的量測；改後在 0 ms 量到 7.2–7.5 秒，見下方「寫入恢復比選舉晚一點」。）

- **選舉時間約 5 到 7 秒，量到的範圍內看不出和 RTT 有關。**
- **寫入恢復比選舉晚一點，約 7 到 8 秒（選舉約 6 到 7 秒）：** 2026-11-23 量（三節點，同一台主機的 Docker，RTT 0，停掉 leader；原始數字在 `tools/cluster-latency/results/hiqlite-fast-reconnect/`）：選舉 6.3 到 6.7 秒，第一次寫入成功在 7.2 到 7.5 秒，即選舉後約 0.5 到 1 秒；同樣條件下改前的版本是 15.1 到 15.5 秒（3 次）。原因：叢集資料庫的用戶端（hiqlite 0.16）把「現在的 leader 是誰」快取起來，只在它重連的迴圈裡更新；原版重連是前 5 次每 1 秒、之後每 5 秒，選舉在第 5 秒之後才完成時，要再多等一次 5 秒。現在 rradius 載入一份修改過的 hiqlite（`vendor/hiqlite`，只把 5 秒改成 1 秒，見該目錄的 `MODIFICATIONS`），所以每秒重連一次；這段時間節點記錄每秒一行 `Could not connect Client API WebSocket to node1`（舊 leader），每個請求 5000 ms 的資料庫預算（`[lua] query_timeout_ms`）也會逾時。企業版從核心 `7ebaddd` 起也載入同一份修改，量到 6.1 到 7.1 秒；這個間隔是 hiqlite 內部的常數，沒有設定可以調。
  - **實驗：** 三節點、節點間 RTT 約 0、一台主機的 Docker，殺掉 leader，兩個存活節點各自量第一個成功的寫入。shipped 版本 3 次都是 15.1 秒（選舉 6.3 到 7.1 秒）；在複本裡把 5 秒的間隔改成 1 秒後是 7.2、7.2、6.1 秒（選舉 5.7 到 7.1 秒），寫入緊跟在選舉之後。原始數字、重算方式與重跑步驟在 `tools/cluster-latency/results/stall-experiment/` 與該目錄的 `README.md`。
  - **限制：** 每種只量 3 次，只在 RTT 約 0 的單機 Docker 上量過；較早的 7 到 10 秒與 15 到 18 秒各次，可能與「選舉完成時間落在哪一次嘗試之前」有關，但沒有逐次核對；廣域網路與選舉更久的情形沒有量。修補要在 hiqlite（已備好給上游的說明，尚未送出），rradius 這邊沒有改。
  - **對規劃的影響：對照上方〈架構〉表格和〈移除節點〉寫的「幾秒」，規劃時寫入中斷要抓 20 秒左右，不是 5 秒。**
- 登入（讀）不受影響，仍讀本機副本。

### 分區

用 `netem` 把節點之間的封包全丟（兩個方向），RADIUS 用戶端路徑不受影響。每種情形做 1 次，分區後約 5、12、22、32 秒取樣，每次對每個節點各送一個 `pap` 和一個計費 Start（逾時 2 秒）。RTT 0.2 與 20 ms 結果相同，除非另外註明。

| 情形 | 被隔開的節點 | 多數方 | 恢復（網路接回後） |
| --- | --- | --- | --- |
| 隔開一個 follower | 登入照常回應（讀舊副本）；計費不回應；約 10 秒內 `rradius_cluster_leader` 變 0，`seconds_without_leader` 一路增加；`applied_index` 停住（32 秒時 14 對 20；29 對 32） | 計費只有 leader 回應（0.2 ms 時兩台都回應；20 ms 時另一台 4 次取樣都沒有回應）；登入正常 | 追上 24.8 秒（0.2 ms）、29.3 秒（20 ms）；經它寫入約 25.3、29.8 秒 |
| 隔開 leader | 登入照常回應；計費不回應；`rradius_cluster_is_leader` 仍是 1 但 `rradius_cluster_leader` 約 10 秒後變 0；`applied_index` 停住 | 選出新 leader（0.2 ms 時第 12 秒、20 ms 時第 22 秒的取樣已可見）；**32 秒取樣時計費仍然沒有回應**（包括新 leader）；登入正常 | 追上 1.3 秒（0.2 ms）、1.6 秒（20 ms）；舊 leader 退為 follower |

- **符合上方〈架構〉一節寫的「被隔開的節點讀舊資料」：** 被隔開的節點副本停在分區當時，照常回應登入。不能接受的話設 `stop_without_leader_ms`（這次沒有設，也沒有測設了之後的行為）。
- **多數方的計費寫入在 leader 換人後要很久才恢復，** 這次觀察到分區後 32 秒仍沒有恢復。可能和上面殺掉 leader 是同一個原因，但分區時舊 leader 還活著，沒有驗證。
- **隔開 follower 後的恢復時間，隨隔開多久而變長，原因是 leader 到它的那條 TCP 連線卡在重傳的倒數裡。** 2026-11-20 補量（`tools/cluster-latency/follower_heal.py`，0 RTT，每種長度 1 次，三節點在一台 Docker 主機）：隔開 4、12、30、60 秒，接回後到「這個節點知道 leader、追上資料、經它寫入有回應」分別是 4.9、15.2、25.5、49.8 秒。要追的資料只有 3 到 12 筆，不是同步慢。查到的原因：分區時 leader 對這個 follower 的 Raft 連線（埠 8100）有資料送不出去，Linux 對沒有回應的連線把重傳間隔每次加倍（0.2、0.4、0.8 秒……，`ss -tno` 看得到 `Send-Q` 增加、重傳次數從 4 增到 6），接回後要等下一次重傳才送得出去，下一次重傳離現在多遠，就和隔開了多久差不多（隔開 12 秒等到第 25 秒、30 秒等到第 51 秒、60 秒等到第 102 秒）。接回後約 1 秒內新連線就建好了，卡住的是舊連線。把節點的 `net.ipv4.tcp_retries2` 從預設 15 降到 5（連線在約 12.6 秒沒有回應後就被核心放棄、重連）後，隔開 12、30、60 秒的恢復變成 5.1、7.6、5.1 秒。這個設定是整個容器的網路命名空間共用，影響所有 TCP 連線；Docker 的 compose 可以用 `sysctls:` 設，**Kubernetes 要叢集允許這個 sysctl，沒有試過。** 只量了一次，沒有量更短的值，也沒有量對 leader 被隔開的情形的影響（那一種本來就很快）。hiqlite 的 Raft 連線沒有自己的「很久沒回應就重連」（它的客戶端串流有 35 秒的這種檢查），讓 hiqlite 在 Raft 連線上也這樣做是更根本的處理，還沒有向上游提。

### 滾動升級

先量出該 RTT 的最高寫入吞吐，取一半，平均分給三個節點，每個節點各一支 `rradius-bench`（`acct-start`，固定速率，逾時 1 秒，不重送）；另外每個節點各有一個每 50 ms 一次的寫入探測。一次一台（先兩個 follower，最後 leader）`docker stop -t 30`、`docker start`，等記錄出現 `cluster node N has caught up with the cluster`。

| 節點間 RTT（實測） | 負載（共） | 每台停止到追上 | 停止本身 | 逾時的請求 | 升級時其他節點的最長空檔 | 被升級節點自己的最長空檔 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.2 ms | 21,600／s | 15.9、17.6、21.3 秒（leader 最後 21.3） | 14.6 秒 | 每個節點 5,500–6,500 個，約 0.2–0.3%（每個節點約 258 萬個） | 0.1–1.4 秒 | 10.8–15.9 秒 |

- **一台一台升級，另外兩台一直有回應。** 逾時的請求大部分是送給正在停機那一台的（用戶端沒有改問別台）。
- **升級一台的時間約 16 到 21 秒（停止約 15 秒，加上啟動追上）**；leader 那台最久。**停 leader 時其他節點的寫入空檔最長，0.2 ms 時 1.4 秒，20 ms 時 6.9 秒。**
- 沒有測：升級的新舊版本混在一起（這次是同一個映像重啟）、資料量大時追上的時間。

### 三種拓撲

| | 跨三個機房的單一叢集 | 主叢集加冷備援 | 各機房獨立叢集 |
| --- | --- | --- | --- |
| 做法 | 三個節點分在三個機房，同一個叢集 | 一個機房跑叢集；另一個機房平時沒有節點，用企業版的 `[cluster.backup]` 定期存副本（見企業版手冊），出事時把副本還原成新叢集 | 每個機房一個三節點叢集，互不相干 |
| 登入（讀） | 不受影響（量到 0.7 ms） | 同主叢集 | 同單機房 |
| 寫入（IP 配發、驗證碼、計費） | 每次約 3 到 4 個 RTT；並行 64 時 20 ms 約 830／s、50 ms 約 320／s | 同單機房 | 同單機房 |
| 一個機房整個失聯 | 剩兩個機房有多數；選舉約 5 到 7 秒，寫入中斷抓 20 秒左右 | 主機房失聯就要靠還原，會丟掉上一份副本之後的寫入；切換要人操作 | 其他機房不受影響；失聯機房的用戶要靠別處 |
| 代價 | 寫入慢、升級期間的空檔變長；要自己確認真實網路比模擬的差多少 | 備援機房平時沒有熱資料；沒有量還原需要多久 | 帳號、設定、migration 要在每個叢集各做一次，一致性自己管 |

- **熱備援（備援機房常駐一個只複製、不投票的節點）目前做不到：** 新節點先當 learner、複製完就自動升成投票成員，沒有讓它一直當 learner 的設定。
- 「主叢集加冷備援」的還原時間、「各機房獨立叢集」的帳號同步方式，這次都沒有量。

### 沒有測的部分

抖動與封包遺失、兩個方向延遲不同、實體主機與經過 WireGuard 的環境、真實 NAS 在選舉期間的重送行為、對 follower 送寫入的吞吐、更高的並行、五個節點、設了 `stop_without_leader_ms` 的分區、計費暫存在高延遲下的行為、分區超過 30 秒、備份還原花的時間。

## 常見問題

| 現象 | 原因 |
| --- | --- |
| 啟動後一直沒有 `listening`，最後以狀態碼 1 結束 | 等不到多數節點：其他節點沒啟動、WireGuard 不通、防火牆擋住、`raft.secret` 不同 |
| 某台的登入結果和其他台不同 | 那台的副本落後（看 `rradius_cluster_applied_index` 和其他台比），或被隔開了（`rradius_cluster_leader` 是 0），或 `migrations/` 不同；看那台的記錄 |
| 停一台之後計費變慢 | 停的不是 leader 時不應該。停的是 leader 時，約 7 到 8 秒內寫入會逾時並進暫存（選舉約 6 到 7 秒）。停兩台時，沒有 leader 超過 5 秒後寫入立刻失敗並進暫存 |
| 有些登入沒有回應，`reason="database"` 在增加 | 那台連不到叢集資料庫（沒有 leader、被隔開）或資料庫太慢。看 `rradius_cluster_leader` 和記錄 |
| 某一台完全不回應，`reason="no_leader"` 在增加 | 設了 `stop_without_leader_ms`，那台沒有 leader 太久。恢復它和其他節點之間的網路 |
| Wi-Fi 登入偶爾失敗，記錄提到 `State` | EAP 對話的後半段到了另一個節點。NAS 改成主備，或負載平衡器依來源固定節點 |
